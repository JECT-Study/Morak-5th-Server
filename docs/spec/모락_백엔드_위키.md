## 1. 서비스 개요와 범위

- 서비스명 **모락**, 캐릭터 **모락이**. 같은 목표의 사람들이 챌린지 그룹을 만들어 매일 사진 인증을 하는 웹앱.
- 마감 2027-01-09. 10월 말~12월 초 개발, 12월 초~1월 초 베타(14일 챌린지 2회), 1월 9일 결과 정리.
- 북극성 지표: 완주 그룹 비율 50% (= 예정 기간을 마치고 팀 달성률 90% 이상으로 종료한 그룹 ÷ 시작한 그룹). 조기 종료 그룹은 분모에만 들어가고, 시작 전 폐기 그룹은 양쪽에서 제외.
- **1차 MVP 제외**: 프로젝트(링크 인증) 유형, AI 추천·검수, 결제·충전·현금 환급·구독, 랭킹·신고, 진행 중 합류, 합류 후 자진 탈퇴, 신청 취소, 인증 재제출·이의 제기, 운영진 일괄 판정, 같은 멤버로 다시 하기, 포인트로 프로필 꾸미기, 1:1 채팅·채팅 이미지 첨부, 메시지 수정·삭제.
- 챌린지는 **데일리 사진 인증만** 있다(모든 챌린지가 같은 기능). 카테고리: 운동, 공부, 커리어, 독서, 생활습관(단일 선택, 온보딩 관심 분야와 같은 목록).

## 2. 용어와 역할

| 용어 | 정의 |
|---|---|
| 포인트 **P** | 서비스 내 무료 활동 포인트. 현금 가치·교환 불가. **"보증금", "예치금", "현금" 표현 금지** (법무, PRD 법 관련 절) |
| 참여 포인트 | 공개 챌린지 신청 시 거는 포인트. 1인 1,000~5,000P |
| 팀 달성률 | 전체 성공 인증 횟수 ÷ 전체 인증 대상 횟수. 정산 기준 |
| 개인 인증률 | 모든 참여 챌린지 누적 승인 ÷ 누적 인증 의무. 프로필·모락이 기준 |
| 보류 | 포인트 없는 챌린지에서 방장·부방장 판정을 기다리는 인증 상태 |

| 퇴장 고려 대상 | 퇴장 공지를 받고 실제 퇴장 전까지의 유예 상태(휴면) |
| 완주 횟수 | 퇴장 없이 예정 기간 끝까지 참여한 챌린지 수 (메달 기준) |
| 중도 실패 챌린지 횟수 | 개인 실패 누적으로 퇴장한 챌린지 수 |

| 역할 | 정의와 권한 |
|---|---|
| 방장 | 챌린지 개설자. 지원 승인·거절. 포인트 없는 챌린지에서 **자신을 제외한 모든 팀원(부방장 포함)의 인증을 판정** |
| 부방장 | 개설 후 **처음 실제 합류한 사람**. 포인트 없는 챌린지에서 **방장의 인증만** 판정. 방장 이탈 시 방장을 이어받음 |
| 참여자 | 인증 제출, 피드·채팅 이용 |
| 운영진 | 포인트 공개 챌린지의 **모든 참여자(방장·부방장 포함) 인증**을 개별 승인·거절. 초기에는 개발팀 |

공개 챌린지는 방장 포함 3~10명, 비공개는 2~10명. 방장도 인원에 포함되고 다른 참여자와 똑같이 인증한다. [확정, FRD §2]

## 3. 공통 규칙

- **시간대**: 모든 날짜·마감은 **KST(UTC+9)** 기준. DB의 `DATE`는 KST 날짜, `DATETIME(6)`은 UTC. 스케줄러는 `zone="Asia/Seoul"`을 명시한다 (AWS 기본 UTC). [확정/QA]
- **날짜 경계**: 인증 마감 당일 23:59. 다음 날 00:00부터 전날 인증은 제출 불가. 광고·출석 횟수도 KST 자정 초기화.
- **포인트 정수 처리**: 모든 포인트·비율 계산은 정수 연산. 반올림은 **소수 첫째 자리에서 반올림(half-up)**: 1,024.6→1,025, 1,024.5→1,025. [확정, FRD §F04]
- **멱등성**: 포인트 원장·알림·정산은 모두 멱등키로 중복 실행을 막는다 (6절).
- **FK 규칙**: FK는 같은 도메인 안에서만 건다. 다른 도메인은 ID만 저장.

## 4. 도메인별 스펙

### 4.1 유저·온보딩·프로필

**온보딩 [확정, FRD F07]**
- 3화면: 정보 입력 → 이용 안내 → 완료. **이용 안내의 "확인했어요"에서 온보딩 완료 + 가입 포인트 10,000P 1회 지급**. 완료 화면 재진입·버튼 중복으로 중복 지급 금지.
- 입력: 닉네임(필수, 중복 불가), 한 줄 소개·관련 링크(선택), 관심 분야 최소 1개(복수). 프로필 사진은 마이페이지에서 설정.
- 건너뛰기 없음. 중단 후 재진입하면 처음부터.
- 구현: `users.onboarded_at` NULL=미완료. 지급은 원장에 `SIGNUP:{userId}` 키로 1회만.

**프로필 [확정, FRD F05]**
- 타인에게 보이는 것: 개인 인증률, 모락이 단계, 획득 메달, 누적 완주 횟수, 중도 실패 챌린지 횟수. 승인 대기 목록은 **본인 전용**(타인 비공개).
- 개인 인증률(%) = 누적 승인 ÷ 본인에게 의무가 있었던 누적 횟수 × 100. **챌린지별 평균이 아니라 횟수 합산**. 미제출도 분모. 미래 인증과 면제일은 제외. 퇴장자는 공지 전까지의 의무·승인만 계산. 퇴장 자체는 감점 없음.
  - 예: 의무 15회+10회 중 20회 승인 → 20÷25=80%.
  - [제안, D-12] 분모에는 판정이 끝난 행(`APPROVED`, `AUTO_APPROVED`, `REJECTED`, `FAILED`)만 포함하고, 판정 대기(`PENDING`)는 분모·분자 모두에서 뺀다. (FRD는 "보류는 실패로 확정하지 않는다"까지만 명시)
  - 진행 중 챌린지도 포함하므로 `participation_result`(종료 확정본)만으로는 계산할 수 없다. `certification`을 합산한다. 느려지면 캐시 테이블을 추가한다.
- 모락이 단계: 95%↑ Stage5 / 85~95 Stage4 / 60~85 Stage3 / 30~60 Stage2 / 30↓ Stage1. 경계값은 아래 단계에 속함(정확히 30→2, 60→3, 85→4, 95→5). 인증 기록이 없으면 Stage1이 아니라 **"인증 기록 없음" + 기본 캐릭터**.
- 완주 횟수 +1: 퇴장 없이 예정 기간 끝까지 참여한 정상 종료 챌린지. 팀 달성률·포인트와 무관. 중도 실패 +1: 퇴장한 챌린지. **조기 종료 남은 2명은 둘 다 증가 없음**.
- 메달: 완주 1·3·5·10·20·30·50회 → 메달 1-1, 1-2, 1-3, 2-1, 2-2, 2-3, 3. 기존 메달 유지(누적 최대 7종). 조건은 코드 enum으로 `medal.code`(`COMPLETE_N`)에 연결.

**회원 탈퇴 [제안, D-3]**: 진행·시작 대기 중인 챌린지(방장 포함)가 있으면 탈퇴 불가. 없으면 탈퇴하고 개인정보를 비식별화하며 인증 사진·채팅은 "탈퇴한 사용자"로 남긴다(기록 보관 방침).

### 4.2 챌린지 (개설·모집·시작)

**개설 입력 [확정, 화면 §6]**

| 항목 | 규칙 |
|---|---|
| 챌린지명 | 12자 제한(앱 검증) |
| 공개 여부 | 공개(탐색 노출) / 비공개(링크·코드로만). **개설 후 전환 불가** |
| 카테고리 | 단일 선택 |
| 한줄 소개 | 필수. `description`에 저장 |
| 주요 목적 | 선택. `purpose`에 저장 |
| 공통 미션 | 하루 하나의 공통 미션 |
| 인증 방법·규칙 | 판정 기준. **개설 후 변경 불가** |
| 기간 | 시작일은 KST 기준 내일부터 선택, 시작일·종료일 포함 **최소 7일**(`end_date >= start_date + 6`), 상한 미정 |
| 정원 | 공개 3~10, 비공개 2~10 (방장 포함). 개설 후 축소 불가 |
| 바라는 점 | 선택 |
| 참여 포인트 | **공개에만** 설정. 걸면 1,000~5,000P. 개설 후 변경 불가. 비공개는 포인트 불가 |

- 개설 시 방장은 `ACTIVE` 참가자(role=HOST)로 등록. 동시 참여 5개 한도에 포함된다(초과 시 개설 불가).
- 참여 포인트가 있는 공개 챌린지는 개설과 방장 등록을 처리하는 트랜잭션에서 방장도 같은 포인트를 건다. 잔액이 부족하면 개설할 수 없다. 원장 키는 `HOLD:{participationId}`.
- 참가 연동 전에는 개설 API가 `503`을 반환한다. 무효화된 대기 신청이 있고 알림이 연동되지 않은 경우에도 `503`을 반환하고 개설을 롤백한다. 포인트 연동 전에는 포인트가 설정된 개설 요청과 대기 신청의 포인트 처리가 필요한 개설 요청도 거절한다.
- 초대 링크·코드: **공개·비공개 모두 발급**. 코드는 6자리 문자열이다. 숫자 전용인지 영문도 포함하는지는 [OPEN, O-5]이며, 현재 구현은 숫자만 발급한다. 유효하지 않은 코드 → "유효하지 않은 코드입니다". 종료·폐기된 챌린지 → "이미 종료된 챌린지입니다".
- 진행 중 미션·인증 규칙·정원·공개 전환 변경 불가.

**챌린지 상태 `challenge.status` [확정+제안]**

```
RECRUITING ──(시작일 00:00, 인원 충족)──▶ IN_PROGRESS ──(종료일 경과)──▶ FINALIZING ──(마지막 판정 완료·정산)──▶ ENDED
    │                                          ▲
    └─(시작일 00:00, 인원 미달)─▶ START_HELD ──(연장 중 인원 충족: 다음 00:00)──┘
                                      │
                                      └─(방장 폐기 / 연장 종료 자동 폐기)─▶ DISCARDED
```

- `RECRUITING` 중 정원이 다 차면 **모집 마감**(지원 차단)이지만 시작일은 당겨지지 않는다 (QA, CASE 1). 상태값은 그대로 `RECRUITING`, "모집 마감"은 `current_count = capacity`로 계산해 표시.
- 모집 중인 챌린지의 시작일은 **방장이 바꿀 수 없다**(QA). 시작일이 바뀌는 경우는 아래 두 가지뿐.

**시작 처리 (시작일 00:00) [확정, FRD F02·화면 §6]**
- 승인되어 실제 합류한 인원(방장 포함, **승인 대기 제외**)이 최소 인원(공개 3 / 비공개 2) 이상이면 `IN_PROGRESS`.
- 미달이면 `START_HELD`(시작 보류). 방장에게 알림 #4. 자동으로 **3일 추가 모집**.
  - 마감 = **예정 시작일을 1일째로 센 3일째 23:59** (예정 시작일 + 2일). 예: 11/1 시작 예정 → 11/3 23:59.
  - 마감까지 인원이 안 차고 방장이 선택하지 않으면 **다음 날 00:00에 자동 폐기**(알림 #7).
  - 연장 중 최소 인원이 차면 **다음 날 00:00 자동 시작**하고, 이때를 기준으로 챌린지 일수를 센다. [제안, D-10] 기간 길이는 유지: `start_date = 시작되는 날`, `end_date = start_date + (원래 일수 - 1)`.
  - 같은 00:00 배치에서는 **"시작(충족) 검사"를 "자동 폐기" 검사보다 먼저** 한다.
- 방장 선택 (`START_HELD` 중, 방장만 가능):
  - **기간 재설정**: 새 시작일·종료일 입력(최소 7일 유지). 다른 시작 대기 참여자에게 알림 #5. 상태는 `RECRUITING`으로 돌아간다.
  - **폐기**: `DISCARDED`. 모든 참가자의 걸린 포인트 즉시 전액 반환. 알림 #6. 시작 후에는 임의 폐기 불가.
- 시작 전 폐기(수동·자동)된 참가자는 완주·통계에 기여하지 않고 `participation_result` 행도 만들지 않는다.

### 4.3 참가 (지원 → 승인 → 참여)

**모든 진입 경로가 같다 [확정]**: 탐색·초대 링크·초대 코드 → 챌린지 상세 → **지원서(각오 한마디) 작성** → 방장 승인 → 참여 확정. 링크·코드 접속만으로 합류하지 않으며, 비공개·포인트 없는 경우도 승인을 생략하지 않는다.

**참가 상태 `participation.status`**

```
PENDING ─승인→ ACTIVE ─(실패 누적 기준 도달 공지)→ EXPEL_NOTICED ─(다음 날 00:00)→ EXPELLED
   │              │
   │              ├─(예정 기간 끝까지 퇴장 없음)→ COMPLETED
   │              └─(공개 챌린지 2명만 남음)→ EARLY_ENDED
   ├─거절→ REJECTED
   ├─(5개 한도 도달)→ INVALIDATED
   └─(시작 전 폐기)→ DISCARDED   (ACTIVE도 폐기 시 DISCARDED)
```

- **취소·자진 탈퇴는 없다.** 제출 후 취소 불가, 승인 후 시작 전에도 탈퇴 불가. 퇴장은 개인 실패 누적으로만 일어난다. 거절·무효 후 **재지원 불가**(한 챌린지에 한 번만). 합류 후 안내 문구는 지원 시점에 노출(UI).
- 거절 사유는 제공하지 않는다.

**지원 (포인트 공개 챌린지) — 한 트랜잭션 [확정]**
1. 사용자 포인트 계정 행 잠금.
2. 동시 참여 5개 한도 확인 (아래).
3. 챌린지가 모집 가능한 상태(`RECRUITING` 또는 `START_HELD`)이고 모집 마감이 아닌지 확인.
4. 잔액 ≥ 참여 포인트. 부족하면 **신청을 완료하지 않고** 광고·출석 획득 방법을 안내(결제 화면 없음).
5. 원장 `HOLD` 기록(`HOLD:{participationId}`), `point_status=HELD`, 참가자 `PENDING` 생성.
- 포인트 없는 챌린지는 2·3만 확인. 잔액 0이어도 지원 가능.
- 승인 대기자는 채팅 접근 불가. 대기 인원은 정원을 넘을 수 있다(정원 확인은 승인 시점).

**동시 참여 한도 5개 [확정, FRD F01]**
- 대상: **내가 개설한 방 + 승인되어 시작을 기다리는 방 + 진행 중인 방**. 공개·비공개·포인트 유무 무관 합산. 승인 대기 신청과 종료된 방은 제외. 같은 방 중복 집계 없음.
- 구현 해석 [제안]: `participation.status IN (ACTIVE, EXPEL_NOTICED)` 이고 챌린지 상태가 `RECRUITING / START_HELD / IN_PROGRESS`인 건수.
- 이미 5개일 때 지원 → "참여 가능한 챌린지를 초과했습니다", 차단.
- **개설 또는 승인으로 5개가 되는 순간** 그 사용자의 다른 `PENDING`은 전부 `INVALIDATED`:
  - 걸린 포인트 **즉시 전액 반환**(방장 확인을 기다리지 않음, 차감 없음). 원장 `REFUND:{participationId}`.
  - 방장에게 알림 #3 + "확인" 버튼. 확인하면 `invalid_confirmed_at` 기록, 승인 대기 목록에서 사라짐. **확인 전에도 승인 불가**. 한도가 풀려도 복원되지 않는다.
  - 신청자 본인의 대기 목록에서도 유효한 신청으로 보이면 안 된다.

**승인 (방장) — 한 트랜잭션 [확정]**
1. 챌린지 행 잠금. 신청이 `PENDING`(무효 아님)인지, 정원 `current_count < capacity`인지 확인.
2. `ACTIVE`, `joined_at` 기록, `current_count + 1`. 신청자에게 알림 #1.
3. **개설 후 처음 합류한 팀원이면 `role=DEPUTY`** 로 지정하고 알림 #8.
4. 신청자가 이 승인으로 5개가 되면 그 사람의 다른 `PENDING`을 무효화(위 절).
5. **정원이 차는 순간 남은 모든 `PENDING`을 거절 처리**하고 포인트 전액 반환, 알림 #2 (예: 승인 3명 남았는데 대기 9명이면 3명째 승인 직후 나머지 6명 거절). [확정, QA]
- 거절: `REJECTED` + 포인트 즉시 전액 반환 + 알림 #2.

**방장·부방장 승계 [확정, FRD F02/§2]**
- 방장이 이탈(퇴장 포함)하면 **부방장이 방장**이 된다. 남은 참여자 중 **합류 순서(`joined_at`)가 가장 빠른 사람이 새 부방장**.
- 부방장이 퇴장해도 같은 규칙으로 새 부방장 지정.
- 판정 담당은 role로 계산하므로(4.4) role만 바꾸면 미처리 인증이 새 담당자에게 자동으로 넘어간다.
- 비공개에서 1명만 남는 경우는 "폐지" [확정, FRD]. 의미는 [제안]: 2명 미만이 되면 그날 종료하고(포인트 없음) 기록은 보관.

### 4.4 인증·판정·퇴장

**인증 제출 [확정]**
- 하루 1회, 사진(촬영 또는 앨범), 당일 **23:59까지**. 제출 후 **수정·삭제·재제출 불가**. 한 사람이 한 날짜에 한 건(`UNIQUE(participation_id, cert_date)`).
- 마감 후 제출·미제출은 **실패**. 미제출은 **00:00 배치가 `FAILED` 행을 만든다**(제출 시각 NULL).
- 퇴장 공지된 사람, 조기 종료일, 면제일에는 제출·`FAILED` 생성 모두 하지 않는다.

**인증 상태 `certification.status`**

| 상태 | 의미 | 피드 노출 | 집계 |
|---|---|---|---|
| `PENDING` | 판정 대기. 포인트 챌린지=검수 중(운영진), 그 외=보류(방장·부방장) | X | 미확정 |
| `APPROVED` | 승인 | O | 성공 |
| `AUTO_APPROVED` | 정오 자동 승인(포인트 없는 챌린지만) | O | 성공 (승인과 동일) |
| `REJECTED` | 거절 | X | **실패** |
| `FAILED` | 미제출 또는 마감 후 제출 | X | **실패** |

- 판정 담당 구분: **`challenge.point_amount > 0` 이면 운영진**, 아니면 방장·부방장. `judge_due_at`이 NULL이면 운영진 판정(자동 승인 없음).
- **피드에는 승인된 사진만** 노출. 보류·검수 중·거절 사진은 다른 팀원에게 보이지 않는다. 좋아요·답글은 성공 여부에 영향 없다.

**판정 담당 [확정]**

| 챌린지 유형 | 판정자 | 대상 | 마감 | 미처리 시 |
|---|---|---|---|---|
| 포인트 없는 공개·비공개 | 방장 | 자신 외 모든 팀원(부방장 포함) | 인증 다음 날 12:00 | 정오 자동 승인 + 담당자 경고 |
| 포인트 없는 공개·비공개 | 부방장 | **방장 인증만** | 인증 다음 날 12:00 | 정오 자동 승인 + 담당자 경고 |
| 포인트 공개 | 운영진 | 모든 참여자(방장·부방장 포함) | 다음 날 검수 (**마감 시각 [OPEN]**, D-1) | **자동 승인·경고 없음** |

- 방장 본인 인증은 방장이 판정할 수 없다. 부방장 본인 인증은 부방장이 판정할 수 없다(방장이 판정).
- 포인트 챌린지에서는 방장·부방장에게 판정 버튼·업무 경고가 없다.

**정오 자동 승인과 경고 [확정]**
- 매일 12:00: 포인트 없는 챌린지의 전날 제출분 중 `PENDING`을 모두 `AUTO_APPROVED`로 전환하고 피드에 공개. 이미 거절된 것과 미제출(`FAILED`)은 그대로.
- **경고는 담당자별 하루 1회**(미처리 사진이 4장이어도 1회). 방장과 부방장은 각자 따로 쌓인다. 예: 방장이 4건 미처리, 같은 날 부방장이 방장 사진 미처리 → 방장 1회, 부방장 1회.
- 누적 **2회부터** 팀 채팅에 시스템 메시지로 공개, 이후 추가될 때마다 공개. [확정, 2회: PRD·화면·QA·FRD 본문. FRD 용어표의 "3회"는 오기로 보고 정정 요청 — D-6]
- 경고는 **개인 미션 실패·퇴장과 무관**하다. 알림 #9로 본인에게 통지.
- 구현: 경고 횟수는 별도 테이블 없이 **`AUTO_APPROVED` 인증의 (판정 담당, cert_date) 고유 개수**로 센다. 채팅 공개 메시지는 알림 `dedup_key`로 하루 1회만 올린다.
- [제안, D-7] 경고 페널티 확장(권한 이관, 프로필 표시, 방 개설 제한)은 **MVP 제외**. 도입하면 `judge_participation_id` 컬럼과 집계 테이블이 필요하다.

**퇴장 [확정]**
- 개인 누적 실패(`fail_count`: 미제출·거절·마감 후 제출) **≥ ceil(예정 인증 횟수 × 15%)** 이면 퇴장 대상. 올림, **정수 연산**: `threshold = (N*15 + 99) / 100` (N = 예정 인증 일수).
  - 7일→2, 14일→3, 30일→5, 35일→6.
- 퇴장 대상 확정 시 **공지 → 그날은 인증 의무 면제(퇴장 고려 대상, 휴면) → 다음 날 00:00 실제 퇴장**. 공지 후 사용자는 인증 등 행동이 없다.
  - 예: 10/10 실패로 기준 도달, 10/11 공지 → 11일 유예, 12일 퇴장.
- 공지 전까지의 의무·성공·실패 기록은 팀 집계에 유지. **공지일 이후 인증 의무는 팀 달성률 분모·분자 모두에서 제외**.
- 퇴장자는 참여 포인트 **전액 차감**(반환 0). 알림 #10에 실제 퇴장 날짜 표시.
- 방장·부방장도 **본인 미션 실패로** 퇴장될 수 있다(업무 경고로는 퇴장 안 됨). 방장이 퇴장하면 4.3의 승계.
- 판정 시점:
  - 포인트 없는 챌린지: 매일 **12:05** 정오 자동 승인이 끝난 뒤 판정. (QA의 "자정에 퇴장" 의견은 "정오 5분 후 판정·즉시 알림"으로 정리)
  - 포인트 공개 챌린지: [제안, D-4] 그 날짜의 모든 인증 검수가 끝나는 즉시 판정(고정 시각 없음). 일부만 검수된 상태에서 판정하지 않는다.
- [제안, D-11] 공지~퇴장 사이: 인증 제출·채팅 전송 불가, 채팅 읽기는 퇴장 시각까지 가능.
- [제안, D-12] 12:05 공지 전에 이미 제출한 면제일 인증은 집계에서 제외.

**조기 종료 [확정, FRD F02]**
- **공개 챌린지**(포인트 유무 무관)에서 참여자가 실제 퇴장해 **2명만 남은 날** 조기 종료. 비공개는 2명이어도 계속.
- 전날(퇴장 공지일)에 남을 두 사람에게 알림 #11. 종료 당일은 인증 의무 없음, **전날까지만 집계**. 퇴장 공지일에는 즉시 종료하지 않고, 실제 퇴장일에 종료.
- 남은 미판정 인증은 포인트 공개는 운영진이, 포인트 없는 공개는 방장·부방장이 처리. 끝나면 최종 결과 확정, 포인트가 있으면 즉시 정산, 확정일 자정에 채팅 작성 종료.
- 남은 두 사람: 실패 처리 없음, 개인 인증 실적·보관함 유지, **완주·메달·중도 실패 횟수 증가 없음**, 팀 성공으로 표시하지 않음.
- 구현: `end_date`를 조기 종료일로 바꾸고 상태를 `FINALIZING`으로. 남은 참가자 `EARLY_ENDED`.

### 4.5 팀 달성률과 포인트 정산

**팀 달성률 [확정, FRD F03]**
- `팀 달성률 = 전체 성공 인증 횟수 ÷ 전체 인증 대상 횟수 × 100`. **참여자별로 합산**하며 하루 전체를 하나로 세지 않는다.
- 전체 인증 대상 = Σ 참가자별 의무 일수. 의무가 같다면 `인원 × 일수`.
  - 퇴장자: 공지일 이후 일수를 제외. 공지 전 성공·실패는 유지(분자에 성공 포함).
  - 조기 종료: 종료일부터의 일수를 제외.
- 성공 = `APPROVED` + `AUTO_APPROVED`. 판정 대기 인증은 실패로 단정하지 않으므로 **마지막 날 인증까지 모두 판정된 뒤** 확정·정산.
- 구현: 저장하지 않고 정산 시 `certification` 행에서 계산한다.

**정산 (정상 종료, 포인트 공개 챌린지만) [확정]**

| 조건 | 처리 |
|---|---|
| 팀 달성률 **100%** (= 실패가 한 번도 없음) | 기간별 총 반환율: 7~29일 120%, 30~59일 150%, 60~89일 200%, 90일 이상 300% (원래 포인트 포함) |
| 90% 이상 ~ 100% 미만 | 참여 포인트 **전액** 반환 |
| 90% 미만 | `참여 포인트 × 팀 달성률` 반환, 나머지 차감 |
| 퇴장자 | **0 반환**, 전액 차감 (팀 결과 무관) |

- 비례 계산은 표시용 비율을 쓰지 않고 **원래 횟수 비율**로. 최종 반환량은 소수 첫째 자리 반올림 정수. 차감 = 참여 포인트 − 반환량.
  - 정수식(half-up): `(2*P*s + r) / (2*r)` (P=포인트, s=성공, r=대상).
- 퇴장자의 과거 실패가 남아 있으면 팀 달성률이 100%가 아니므로 기간별 추가 보상은 없다.
- 포인트 없는 챌린지는 반환·차감이 없다.
- 팀 달성률 100% 보너스(120~300%)로 늘어나는 포인트의 출처는 [제안, D-5]: **시스템이 신규 발행**(원장 `SETTLE`, 사유 `TEAM_RATE`), MVP는 재원·상한 없이 정산 합계로 모니터링.

**조기 종료 정산 [확정]**
- 남은 두 사람 각각 **해당 챌린지의 개인 성공률** = 본인 성공 인증 ÷ 본인 인증 대상(종료 전날까지).
  - 90% 이상 → 참여 포인트 100% 반환. 90% 미만 → `참여 포인트 × 개인 성공률` 반환.
  - **상한 100%, 추가 보상 없음**. 다른 챌린지·팀 달성률은 쓰지 않는다.
- 예: 30일 예정 조기 종료, 각 의무 10회, 5,000P씩. A가 10회 성공 → 5,000P, B가 8회 성공 → 4,000P 반환·1,000P 차감.

**정산 실행 규칙**
- 트리거: 마지막 날 인증까지 판정 완료(= 챌린지 `FINALIZING`에서 미판정 0건) → 결과 확정 → 즉시 정산. 정상 종료는 종료일 다음 날 정오 판정 마감 후, 포인트 챌린지는 운영진 검수가 끝나는 즉시.
- **챌린지당 정산은 1회**. `FINALIZING → ENDED` 조건부 UPDATE와 포인트 지급을 **같은 트랜잭션**에 묶는다. 실패하면 롤백되어 `FINALIZING`에 남고 재시도한다. 원장 멱등키 `SETTLE:{participationId}`로 이중 지급 방지. 정산 후 결과는 바꾸지 않는다.
- [제안, D-9] 오류 시 결과 화면에 "정산 처리 중", 반환 포인트는 잔액에 넣지 않음, 자동 재시도 3회, 계속 실패하면 개발팀 알림.
- 반환 0P(퇴장 등)는 원장 거래를 만들지 않는다. 걸 때의 `HOLD` 기록이 남고, 결과 화면에서 "전액 차감"으로 표시.
- 결과 확정 후: 개인 `participation_result` 행 생성(승인 수, 의무 수, 인증률, 완주 여부, 반환 포인트), 완주 횟수·메달 반영, 채팅은 **확정일 24:00에 작성 종료**(읽기만).

### 4.6 포인트

| 항목 | 규칙 [확정] | 원장 |
|---|---|---|
| 가입 | 온보딩 "확인했어요"에서 10,000P 1회 | `GRANT / SIGNUP_GIFT`, 키 `SIGNUP:{userId}` |
| 앱 방문 출석 | 하루 첫 방문 100P, KST 자정 초기화 | `GRANT / ATTENDANCE`, 키 `ATTEND:{userId}:{date}` |
| 30일 연속 출석 | 30일째 **총 3,000P**(100P 추가 없음), 이후 1일차로 | `GRANT / ATTENDANCE_STREAK` |
| 광고 시청 | 완료 1회 500P, **하루 최대 5회**(최대 2,500P), 자정 초기화. 중간 종료는 지급·횟수 차감 없음 | `GRANT / AD_REWARD`, 키 `AD:{token}` |
| 참여 포인트 걸기 | 지원 시 즉시 차감, 다른 신청에 중복 사용 불가 | `HOLD`, 키 `HOLD:{participationId}` |
| 거절·무효·폐기 | 전액 즉시 반환 | `REFUND`, 키 `REFUND:{participationId}` |
| 정산 | 4.5 | `SETTLE`, 키 `SETTLE:{participationId}` |

- 챌린지당 한도: 1,000~5,000P. 팀 최대 50,000P(10명×5,000P).
- 잔액 변경은 **조건부 UPDATE**로만(`balance >= amount`). 잔액은 음수가 될 수 없다.
- 출석은 앱 진입 시 호출하는 API로 처리한다. KST 날짜 기준 하루 1회, 같은 날 재호출은 성공 응답만. 자정을 넘겨 계속 쓰는 경우는 [제안] 다음 호출 시점의 KST 날짜로 새 출석 판정. (FRD "앱을 계속 사용 중이면" 확인 필요)
- 광고(MVP) [제안, D-8]: **모의 광고**. 시작 API가 서명된 세션 토큰(발급 시각·만료)을 주고, 완료 API가 토큰을 검증(최소 시청 시간·만료·중복)하고 500P 지급. 하루 5회는 **포인트 계정 행을 잠근 채 오늘 지급 건수를 세어** 막는다. 실광고 서버 검증은 플랫폼 확정 후 별도 테이블로 추가.
- 현금 충전·구매·환급·출금·결제 화면은 없다.

### 4.7 팀 채팅 [확정, FRD F02, 화면 §우선순위2]

- **팀 전체 채팅 1개/챌린지**. 1:1 채팅 없음. 텍스트만(임의 이미지 첨부 없음). 메시지 수정·삭제·읽음 표시 없음.
- 접근: **승인(`ACTIVE`) 이후, 시작 전부터** 가능. 승인 대기자는 접근 불가.
- 인증 스토리 답글: 원본 인증을 식별할 수 있는 정보(`reply_certification_id`)와 답글 텍스트가 **팀 채팅 메시지 한 개**로 게시된다(인용 영역에 "{닉네임}님의 인증 스토리에 답장" + 인증 날짜). 별도 댓글 목록 없음.
- 시스템 메시지: 판정 경고 누적 안내(`participation_id` NULL).
- 전송 상태: 전송 중 → 성공 / 실패. **재전송해도 중복 게시하지 않는다** → 클라이언트가 보내는 `client_message_id`로 멱등 처리(`UNIQUE(participation_id, client_message_id)`). 작성 종료 후에는 재전송 불가.
- 종료·퇴장 후:
  - 정상·조기 종료: **최종 결과 확정일 24:00부터 작성 불가**. 끝까지 참여한 사람은 보관함에서 열람.
  - 퇴장: **실제 퇴장 시점까지의 채팅만 읽기 전용**. 이후 메시지·알림 수신 중단. 퇴장자의 인증 사진 열람 범위는 확대하지 않는다.
  - 퇴장 공지~실제 퇴장 사이의 수신은 계속된다(인증 의무 면제와 채팅 수신 중단 시점은 다르다).
- 인증 사진·채팅 기록은 **보관 기한 없이 영구 보관**(보관함).

### 4.8 알림 [확정, FRD 알림 문구]

기본 경로는 **앱 내 알림창**(홈 우측 상단 종 아이콘). 포인트 문장은 포인트를 건 사람에게만 붙인다. 긴 안내(퇴장·조기 종료)는 눌렀을 때 상세를 보여준다. 푸시 채널은 [OPEN, B-9].

| # | 상황 | 받는 사람 | 비고 |
|---|---|---|---|
| 1 | 참가 신청 승인 | 신청자 | "`{챌린지명}` 참여가 확정됐어요" |
| 2 | 참가 신청 거절 (정원 마감 자동 거절 포함) | 신청자 | 포인트 사용 시 "걸어 둔 `{포인트}`P는 전액 반환됐어요" 추가. 사유 없음 |
| 3 | 참여 한도 초과로 신청 무효화 | 해당 신청을 받은 방장 | **확인 버튼**. 확인해야 목록에서 사라짐 |
| 4 | 예정 시작일 최소 인원 미달(시작 보류) | 방장 | 선택 기한 표시(예: 11월 3일 23:59까지) |
| 5 | 방장이 기간 재설정 | 다른 시작 대기 참여자 | 새 시작일·종료일 |
| 6 | 방장이 시작 전 폐기 | 다른 시작 대기 참여자 | 포인트 반환 문장 |
| 7 | 기한 내 미선택 자동 폐기 | 방장과 시작 대기 참여자 전체 | 포인트 반환 문장 |
| 8 | 첫 부방장 지정 | 첫 합류자 | 포인트 없는 챌린지/포인트 챌린지 본문 구분, 눌러서 역할 안내로 이동 |
| 9 | 인증 판정 기한 초과 경고 | 기한 내 판정 안 한 방장·부방장 | 누적 2회 이상이면 "팀 채팅에도 안내" 문장 추가. 포인트 챌린지에는 없음 |
| 10 | 개인 실패 누적으로 퇴장 예정 | 퇴장 대상자 | 실패 횟수, 실제 퇴장 날짜 표시, 포인트 전액 차감 문장 |
| 11 | 공개 챌린지 조기 종료 예정 | 남게 될 두 참여자 | 종료일, 정산 문장(개인 성공률·최대 100%·추가 보상 없음), 상세에서 완주·메달 미반영 안내 |

- 추가로 필요한 알림(문구 미정): 인증 거절 시 "남은 실패 가능 횟수"(QA: "인증 거절 알림 및 남은 카운트 알림"), 정산 완료 알림(QA 제안). 남은 횟수 = `퇴장 기준 − fail_count`.
- 알림은 이벤트로 서버가 자동 생성. 중복 방지: `notification.dedup_key`.

### 4.9 스케줄러 (KST, 모두 멱등)

| 시각 | 작업 | 상세 |
|---|---|---|
| 매일 00:00 | ① 미제출 `FAILED` 생성 | 전날(cert_date) 인증 의무가 있는 `ACTIVE` 참가자 중 제출 없는 사람. 면제일·조기 종료일 제외 |
| 매일 00:00 | ② 시작 처리 | `start_date` 도래 챌린지: 인원 충족 → `IN_PROGRESS`, 미달 → `START_HELD`+알림 #4. `START_HELD` 중 충족 → 시작(기간 재계산). **시작을 폐기보다 먼저** |
| 매일 00:00 | ③ 자동 폐기 | `START_HELD`이고 마감(시작일+2일 23:59)을 지남 → `DISCARDED`, 전액 반환, 알림 #7 |
| 매일 00:00 | ④ 퇴장 실행 | `EXPEL_NOTICED`이고 공지일이 어제 → `EXPELLED`. 그 결과 공개 챌린지가 2명이면 조기 종료(종료일=오늘) |
| 매일 12:00 | ⑤ 정오 자동 승인 | 포인트 없는 챌린지 `PENDING`(`judge_due_at ≤ now`) → `AUTO_APPROVED`. 담당자 경고 집계, 2회부터 팀 채팅 SYSTEM 메시지 |
| 매일 12:05 | ⑥ 퇴장 판정(포인트 없는 챌린지) | 실패 ≥ 기준이면 `EXPEL_NOTICED` + `exempt_from_date=오늘`, 알림 #10. 퇴장 후 2명이면 조기 종료 예정 알림 #11 |
| 이벤트 | ⑦ 운영진 검수 완료 | 그 날짜 포인트 챌린지 인증 미판정 0건 → 퇴장 판정·알림 (D-4). 마지막 날이면 결과 확정·정산 |
| 이벤트/보정 | ⑧ 결과 확정·정산 | `FINALIZING`에서 미판정 0건 → 4.5 정산. 스케줄러가 놓친 건을 줍는 보정 포함 |
| 결과 확정일 24:00 | ⑨ 채팅 종료 | 별도 컬럼 없이 `finalized_at`의 KST 날짜 24:00 이후로 계산 |

- **순서 중요**: 00:00 `FAILED` 생성 → 12:00 자동 승인 → 12:05 퇴장 판정 → 다음 날 00:00 퇴장 실행. 자동 승인 전에 퇴장을 판정하면 안 된다.
- 퇴장으로 인원이 줄어드는 연쇄(승계, 조기 종료)는 ④에서 같은 트랜잭션 순서로 처리.
- 인스턴스가 1대인 동안 분산 잠금은 필요 없다. 늘릴 때 ShedLock 테이블을 추가한다.

### 4.10 운영진 (어드민)

- 문서에 있는 것: 포인트 공개 챌린지의 제출 인증 목록, 인증별 **개별 승인/거절**, **미검수만 보기** (화면 §우선순위2). 일괄 판정은 MVP 제외.
- [제안, D-2] 별도 어드민 서비스 없이 **같은 앱의 `/admin/reviews` 한 페이지**, `users.role=ADMIN`만 접근. 기능: 목록(미검수 필터), 사진 확대, 개별 승인·거절, 챌린지별 검수 현황. 정산 오류는 화면 없이 개발팀이 처리.
- [제안, D-1] 검수 마감은 인증일 다음 날 24:00. 초과 건은 개발팀에 알림, **자동 승인하지 않는다**. 마감 후에도 검수는 가능하며, 끝나기 전까지 그 챌린지의 퇴장 판정·정산은 보류.

**스키마를 확장해야 하는 경우** (지금은 하지 않음): 경고 권한 이관 → `certification.judge_participation_id`. 프로필 경고 표시·개설 제한 → 경고 집계 테이블. 실광고 서버 검증 → 광고 세션 테이블. 서버 다중화 → ShedLock. 인증률 조회 느림 → 누적 통계 캐시.

API 목록은 별도 문서 "모락 API 초안"(Claude Docs)을 따른다. 규칙이 바뀌면 이 위키 → DDL → API 순으로 같이 고친다.

## 6. 구현 가이드 (동시성·멱등)

- 지원·승인·정산·광고·출석은 모두 **한 트랜잭션 + 행 잠금**. 락 순서: 사용자 포인트 계정 → 챌린지 → 참가자 (데드락 방지, 항상 같은 순서).
- 모든 포인트 변동은 `idempotency_key` 유니크로 막는다 (`SIGNUP:`, `ATTEND:`, `AD:`, `HOLD:`, `REFUND:`, `SETTLE:`). 이미 있으면 성공으로 간주.
- 배치는 몇 번 돌아도 결과가 같아야 한다 (상태 조건부 UPDATE, `dedup_key`).
- 계산은 정수. 퇴장 기준 `(N*15+99)/100`, 비례 반환 half-up `(2*P*s + r)/(2*r)`.
- 상태 전이 위반은 예외로 거절하고 로그(예: `INVALIDATED` 승인 시도, `ENDED` 정산 재실행).

| 지원자 9명, 남은 정원 3 | 3명째 승인 직후 나머지 6명 거절 + 전액 반환 |
| 5개 참여 중 지원 | 차단 문구. 개설/승인으로 5개가 되는 순간 다른 `PENDING` 무효 + 즉시 반환 |
| 공개 정원 2·11 / 비공개 1·11 | 설정 불가 |
| 챌린지 기간 6일 | 설정 불가 (최소 7일) |
| 포인트 1,000·5,000 / 999·5,001 | 허용 / 불가 |

## 8. 결정 로그 [제안] — PM 확인 전 구현 기준

| ID | 결정 | 근거·이유 |
|---|---|---|
| D-1 | 포인트 챌린지 **검수 마감 = 인증일 다음 날 24:00**. 초과 건은 개발팀 알림, **자동 승인 없음**. 마감 후에도 검수 가능, 끝나기 전 퇴장 판정·정산 보류 | "다음 날 검수"와 일치. 자동 승인은 포인트 무결성에 위험 |
| D-2 | 어드민 = 같은 앱 `/admin/reviews` 1페이지 + `role=ADMIN` | FE 1명, 초기 운영진=개발팀 |
| D-3 | 방장 이탈 트리거 = **퇴장·회원 탈퇴**만. 앱 삭제·장기 미접속 감지는 MVP 제외. **진행·대기 중 챌린지가 있으면 탈퇴 불가** | 서버가 앱 삭제를 확실히 알 수 없음(푸시 토큰 무효는 재설치 등으로도 발생) |
| D-4 | 포인트 챌린지 퇴장 판정 = **그 날 인증 전건 검수 완료 즉시** | 부분 검수 상태 판정은 이후 거절로 번복 불가 |
| D-5 | 정산 보너스 포인트 = **시스템 신규 발행**(원장 `SETTLE/TEAM_RATE`), 상한 없음, 합계 모니터링 | 무료 활동 포인트. 법 절과 충돌하지 않는지 PM 확인 |
| D-6 | 경고 공개 기준 **2회** (FRD 용어표의 3회는 정정) | PRD·화면·QA·FRD 본문이 2회 |
| D-7 | 경고 페널티 확장(권한 이관·프로필 표시·개설 제한) **MVP 제외** | 스키마·판정 구조 영향 큼 |
| D-8 | 광고 = **모의 광고**(서명 토큰, 최소 시청 시간, 하루 5회). 실광고는 플랫폼 확정 후 | 웹/앱에 따라 연동 방식이 달라짐 |
| D-9 | 정산 오류: "정산 처리 중" 표시, 자동 재시도 3회, 실패 시 개발팀 알림 | QA 제안 수용 |
| D-10 | 추가 모집 중 시작하면 **기간 길이 유지**(`end_date` 재계산) | FRD "이때를 기준으로 일수를 계산" |
| D-11 | 퇴장 공지~퇴장 사이: 인증·채팅 전송 불가, 읽기는 퇴장 시각까지 | QA "행동 없음", FRD 수신 시점 구분 |
| D-12 | 면제일에 이미 제출한 인증은 집계 제외. 개인 인증률 분모는 판정 끝난 행만 | 분모·분자 일관성 |
| D-13 | 검색은 MVP에서 DB 검색(Elasticsearch 제외) | 인프라 구성에 없음, 규모 작음 |
| D-14 | 알림은 인앱 알림함 우선, 푸시는 플랫폼 확정 후 | 채널 미정 |
| D-15 | [확정] 초대 코드는 6자리, 개설 시작일은 KST 기준 내일부터, 포인트 공개 챌린지 방장은 개설과 동시에 참여 포인트를 건다 | 개설 API 구현 전 확인 |
